How it works

Test a policy in three steps

  1. 1

    Write synthetic requests

    Name the remote address, headers, path, and expected decision.

  2. 2

    Set mock DNS answers

    Keep monitor allowlists inside the fixture instead of querying live DNS.

  3. 3

    Run the matrix

    Compare allow, challenge, and block decisions before you edit production rules.

CLI for CI

Run the same checks from one binary

The ppr binary reads YAML or JSON fixture files and emits readable or JSON results.

$cargo install --git https://github.com/B-Divyesh/sf-proxy-policy-rehearsal --bin ppr 
$ ppr demo
Demo uses bundled sample data in a temporary directory.

Supported policy checks

Use the shared matcher subset

Each adapter checks client IP, path, method, and exact headers. Unsupported native behavior is named instead of guessed.

01

Anubis

Checks client IP, request path, method, and header conditions from the shared subset.

Does not parse nested CEL or bot weights

02

Caddy

Checks trusted proxy client IP derivation and the portable request matcher subset.

Does not model handler order or plugins

03

Nginx

Checks real_ip trust with geo and map-style decisions.

Does not model location precedence or regex

Scope and privacy

What this tool does not do

  • It does not query live DNS or IP-intelligence feeds.
  • It does not start, operate, or inspect a production proxy.
  • It does not include telemetry, trackers, or third-party runtime services.
